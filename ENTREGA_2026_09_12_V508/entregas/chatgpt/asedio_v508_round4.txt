EVIDENCIAS EJECUTADAS
1) ctypes ShmHeader: size=128, alignment=128. Por tanto, FIX #47 funciona en esta versión concreta y NO se cuenta como fallo.
2) C++ recompilado como .cpp con GCC/Linux: falla en __declspec(dllexport) antes de enlazar una biblioteca funcional.
3) Tabla de símbolos C++: no se genera .so porque la compilación falla.
4) Varios símbolos FFI requeridos por Python no existen en Rust V508.
5) Rust compiler no está instalado en el entorno, por lo que no se afirma una ejecución Rust real.
6) Colisión SHM reproducida: dos PmtpSlabAllocator con el mismo slab_id comparten exactamente el mismo objeto /dev/shm y pueden observar/escribir los mismos datos.
7) Limpieza SHM reproducida: close() deja el objeto /dev/shm/POLYDIM_SLAB_* existente.
8) Contrato de forma roto reproducido: write_slab_atomic acepta un scalar np.float32 y numpy lo difunde a todo un tensor de 10000 elementos.
9) README afirma 800KB y zero-copy, mientras implementación usada por el código mostrado reserva 320000 bytes y copia con np.copyto/.copy.

NUEVOS HALLAZGOS
P0-FFI-1: Python y Rust declaran conjuntos de símbolos incompatibles.
  Python requiere: pmtp_apply_horizontal_lift, pmtp_route_tensor_su2_seqlock, pmtp_seqlock_get_write_buffer, etc.
  Rust V508 exporta solo: pmtp_seqlock_begin_write, pmtp_seqlock_end_write, pmtp_phase99_swarm_consensus.

P0-FFI-2: El ShmHeader es del mismo tamaño/alineación pero semánticamente incompatible.
  Python offsets 40..127 = _reserved.
  Rust offsets 40=sig_0_off, 48=sig_1_off, 56=write_turn y 57..127=reserved.
  Un test de sizeof/alignment pasa aunque ambos lados puedan interpretar bytes diferentes.

P0-FFI-3: validate_alignment() pasa size_bytes como si fuera element_size.
  Python llama (..., handle.size_bytes, ...); C++ espera element_size.
  Por tanto el camino BF16 (element_size=2) no puede activarse correctamente.
  min_dim se pasa pero C++ no tiene ese argumento.

P0-FFI-4: C++ no comprueba ptr != nullptr. ptr=0 satisface addr % 64 == 0 y puede devolver PASS.

P0-SHM-1: No existe un double buffer en PmtpSlabAllocator. Hay un único tensor_array.
  El README describe Double Buffer y el Rust Header tiene sig_0_off/sig_1_off, pero Python no implementa ninguno.

P0-SHM-2: Seqlock de Python no es atómico y el de Rust no implementa adquisición exclusiva.
  Rust hace fetch_add(1) para begin; dos escritores pueden producir secuencias pares mientras uno todavía está escribiendo.
  Python usa _seq_ptr[0] += 1 directamente.

P1-SHM-3: Identificador de slab no es exclusivo.
  O_CREAT|O_RDWR + nombre fijo permite que dos procesos abran el mismo slab.
  No hay owner/token/epoch/lease ni O_EXCL.

P1-SHM-4: close() no hace unlink en POSIX y además ignora BufferError dejando el mmap vivo.

P1-SHM-5: run_attack_battery() no cierra PmtpSlabAllocator en finally; un fallo del test A7 deja recursos vivos.

P0-MATH-1: Rust modifica local_tensor elemento por elemento y solo después comprueba finitud.
  Con NaN/Inf, puede devolver -7 dejando el tensor del caller ya parcialmente/totalmente corrupto.
  El estado debería validarse antes de commit o escribirse en buffer temporal.

P0-MATH-2: Rust ignora el parámetro dim para el tamaño efectivo; usa D_DIM=10000 en todos los slices/loops.

P0-MATH-3: Rust no valida overflow de num_neighbors * D_DIM antes de crear el slice.
  Con valores grandes, el producto puede desbordar y el tamaño del slice dejar de representar la memoria real.

P0-MATH-4: Rust no valida local_tensor/neighbors/weights para null cuando num_neighbors>0.

P0-MATH-5: dt es un parámetro público pero no participa en la actualización.
  Cambiar dt no cambia la dinámica. Esto contradice la semántica documentada de Euler.

P0-MATH-6: cbf_gamma no implementa una barrera CBF visible; actúa como simple multiplicador escalar.

P1-MATH-7: La proyección I-xx^T solo es una proyección tangente correcta en la esfera unitaria. El código no verifica ||x||=1 antes de usarla.

P1-MATH-8: Si new_norm_sq resulta muy pequeño, el código ya modificó local_tensor antes de retornar -7.

P0-CPP-1: SLERP antipodal exacto vuelve a dividir por norma ortogonal cero para v1=-v0.
  ortho_norm_sq=0 en el caso exacto; ortho_inv_norm=Inf; output puede contener NaN.

P0-CPP-2: SLERP antipodal/near-antipodal usa float ortho[10000]; dim>10000 produce out-of-bounds.

P1-CPP-3: SLERP supone que v0 y v1 están normalizados y tampoco hace clamp real de dot a [-1,1] antes de acosf.

P1-CPP-4: Código de hardware es x86 específico y no representa el soporte de ARM/Neoverse citado en la documentación.

P1-CPP-5: pmtp_cpp_validate_hardware comprueba AVX/XCR0, no AVX-512 aunque el path de alineación devuelve 64 y comenta AVX-512 preferred.

P1-TEST-1: validate_topology() sigue sin return; A1/A2 no pueden demostrar Betti-1.

P1-TEST-2: A6 es una constante local ping=1; no ejerce ninguna llamada FFI.

P1-TEST-3: Fuzzing traga todas las excepciones con `except Exception: pass`.

P1-TEST-4: El test FJLT solo aplica diagonal de signos y compara norma; no ejecuta FWHT, subsampling ni embedding FJLT.

P1-TEST-5: El supuesto zero-copy de Qwen usa np.copy en write/read y no entrega el latent directamente a Model B.

P0-TRITON-1: block puede quedar en un valor no-potencia-de-2. Ejemplo: dim=10000, block=2048 -> OK; pero block=1000 -> 1000. tl.arange requiere tamaños/bounds potencia de dos según documentación actual de Triton.

P0-TRITON-2: run valida x pero no valida dtype/device/contiguidad de out.
  Un out no-contiguous puede recibir stores con indexación lineal incorrecta; out en CPU/dtype distinto falla de forma no contractual.

P1-TRITON-3: assert como contrato de seguridad desaparece con python -O.

P1-TRITON-4: Async cancellation/exception puede liberar idx antes de que termine la operación CUDA.
  finally hace _release(idx) sin esperar event si el coroutine se cancela/lanza después de encolar trabajo CUDA.

P1-TRITON-5: ingest_sync crea un asyncio.run en un ThreadPool cuando ya existe un event loop. _lock es asyncio.Lock compartido y puede cruzar loops, por lo que el diseño no tiene un contrato de loop único.

P1-TRITON-6: close() no impide nuevas operaciones async pendientes ni sincroniza explícitamente CUDA antes de liberar el pool lógico.

P0-ARCH-1: La arquitectura documentada de “Rust FFI Seqlock Double Buffer + POSIX/DLPack + GPU tensors” no corresponde a la implementación V508 entregada.

ORDEN DE CIERRE RECOMENDADO
1) Definir un ABI único y versionado; generar bindings desde una fuente canónica.
2) Reemplazar Seqlock por protocolo de un escritor o CAS odd/even real; separar metadata y payload.
3) Unificar ShmHeader Rust/Python y añadir static assertions de offsets.
4) Hacer dim explícito y validar todas las longitudes/punteros antes de crear slices.
5) Hacer updates transaccionales: calcular -> validar -> commit.
6) Sustituir SLERP antipodal por una construcción geométrica robusta con base ortogonal determinista.
7) Rehacer validate_topology real.
8) Rehacer batería para que pruebe la propiedad que afirma.
9) Corregir Triton: next_power_of_2(block), validar out, y mantener lifecycle CUDA hasta completion incluso bajo cancelación.
10) Separar “zero-copy”, “zero-copy-like”, “shared-memory copy” y “model continuation” como propiedades distintas.

CONCLUSIÓN DE RONDA
No se declara cierre. Los problemas nuevos no son cosméticos: varios invalidan contratos de memoria, ABI o validez matemática. La siguiente ronda debe centrarse en cerrar las invariantes, no en añadir más tests superficiales.
